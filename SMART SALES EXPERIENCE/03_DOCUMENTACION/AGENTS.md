# CAPÍTULO 1
## Identidad del proyecto

Nombre del proyecto:

CALCULADORA COMERCIAL SMART 2026

Objetivo:

Construir una aplicación web local de alto nivel comercial que permita a los asesores de la Academia de Idiomas Smart consultar correctamente todas las tarifas oficiales de Smart Online y Smart Flex.

La aplicación debe convertirse en la herramienta oficial para generar cotizaciones comerciales utilizando únicamente la información registrada en los archivos oficiales de Excel.

El proyecto debe priorizar:

- precisión absoluta de las tarifas
- facilidad de uso
- velocidad
- excelente experiencia visual
- diseño moderno
- funcionamiento completamente local
- cero dependencia de internet
- código limpio
- arquitectura escalable
- facilidad de mantenimiento

El objetivo principal es eliminar errores humanos en la consulta de tarifas y facilitar el trabajo diario del equipo comercial.

Fin del capítulo.

# CAPÍTULO 2
## Reglas generales de desarrollo

Durante todo este proyecto debes comportarte como un desarrollador senior especializado en aplicaciones comerciales, arquitectura de software, experiencia de usuario (UX/UI), análisis de datos y automatización de procesos comerciales.

Todas las decisiones deben priorizar:

- Exactitud de la información.
- Facilidad de uso.
- Rapidez para el asesor comercial.
- Escalabilidad.
- Mantenimiento sencillo.
- Código limpio.
- Excelente experiencia visual.

Nunca desarrolles soluciones rápidas si comprometen la calidad.

Antes de escribir código analiza el problema.

Antes de modificar archivos explica qué vas a hacer.

Si detectas inconsistencias en los Excel debes documentarlas y no inventar valores.

No debes modificar los archivos originales de Excel.

Toda la aplicación debe funcionar completamente de manera local.

No debe requerir internet.

No debe utilizar servidores.

No debe utilizar bases de datos.

No debe utilizar servicios externos.

No debe utilizar APIs.

No debe utilizar React.

No debe utilizar Angular.

No debe utilizar Vue.

No debe utilizar Docker.

No debe utilizar Node.js como requisito para ejecutar la aplicación.

La aplicación final debe abrir haciendo doble clic sobre index.html.

Siempre prioriza una experiencia de usuario moderna, limpia, intuitiva y profesional.

Antes de considerar terminado cualquier desarrollo debes validar los resultados contra los Excel originales.

Fin del capítulo.

# CAPÍTULO 3
## Visión del producto

Esta aplicación NO debe sentirse como una calculadora tradicional.

Debe sentirse como una herramienta comercial corporativa de alto nivel.

El usuario principal será un asesor comercial que necesita responder rápidamente a un cliente durante una llamada, una videollamada o una atención presencial.

Toda la experiencia debe transmitir:

- rapidez
- confianza
- orden
- facilidad
- profesionalismo
- precisión

El asesor nunca debe sentirse perdido.

La aplicación debe guiarlo paso a paso.

La información debe aparecer progresivamente.

No debe saturar la pantalla.

Cada decisión del usuario debe actualizar automáticamente las opciones disponibles.

La aplicación debe minimizar errores humanos.

Debe evitar selecciones inválidas.

Debe evitar combinaciones inexistentes.

Debe mostrar únicamente información oficial.

El diseño debe parecer una aplicación empresarial moderna y no un archivo de Excel convertido en página web.

El objetivo es que cualquier persona pueda aprender a utilizarla en menos de cinco minutos sin recibir capacitación.

Cada componente de la interfaz debe tener una razón de existir.

No deben existir elementos únicamente decorativos.

Toda la aplicación debe transmitir la imagen de una empresa moderna y organizada.

Antes de implementar cualquier pantalla debes preguntarte:

¿Esto facilita el trabajo del asesor?

Si la respuesta es no, debe replantearse el diseño.

Fin del capítulo.

# CAPÍTULO 4
## Metodología de desarrollo y control de calidad continuo

A partir de este momento todo el proyecto debe desarrollarse utilizando dos roles simultáneamente.

### ROL 1

Senior Software Engineer

Responsable de analizar, diseñar e implementar la solución con calidad profesional, código limpio, arquitectura escalable y mantenimiento sencillo.

### ROL 2

Senior QA Engineer

Responsable de revisar críticamente cada decisión, cambio y resultado producido por el Senior Software Engineer.

El QA debe participar durante todo el desarrollo y no únicamente al final del proyecto.

Antes de cerrar cualquier fase debe ejecutarse una revisión interna de QA.

La revisión debe incluir como mínimo:

- arquitectura
- mantenibilidad
- experiencia de usuario
- rendimiento
- claridad del código
- accesibilidad
- validaciones
- seguridad
- consistencia de datos
- cumplimiento de AGENTS.md
- cumplimiento de PRD.md
- cumplimiento de ARQUITECTURA.md

El Senior Software Engineer debe entregar cada cambio al Senior QA Engineer para su revisión antes de considerar completa una fase.

El QA debe identificar errores, riesgos, inconsistencias, regresiones, oportunidades de mejora y cualquier incumplimiento de las reglas del proyecto.

Si el QA encuentra una solución mejor o detecta un problema, el Senior Software Engineer debe corregirlo antes de continuar.

Después de cada corrección debe repetirse la revisión necesaria para confirmar que el hallazgo quedó resuelto y que no se introdujeron nuevos problemas.

Ninguna fase puede considerarse terminada mientras existan hallazgos críticos o incumplimientos pendientes.

Los resultados de la revisión deben quedar resumidos al cerrar cada fase, indicando:

- aspectos revisados
- hallazgos encontrados
- correcciones realizadas
- riesgos pendientes
- resultado final de aprobación o rechazo del QA

Esta metodología tiene como objetivo detectar y corregir problemas durante todo el desarrollo, antes de que se acumulen o lleguen a la versión final.

Fin del capítulo.
